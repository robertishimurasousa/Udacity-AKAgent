# UDA-Hub Acceptance Scenarios

Draft for review linked to the [architecture](README.md). The table lists the expected implementation outcomes. Execution evidence will be recorded in the issue for the corresponding delivery.

| Scenario | Input and procedure | Observable result and evidence |
| --- | --- | --- |
| A01 · Database setup | In a clean directory, run `01_external_db_setup.ipynb`, then run `02_core_db_setup.ipynb` with the expanded knowledge base. Query both databases. | Both notebooks finish without errors. CultPass contains users, subscriptions, experiences, and reservations. UDA-Hub contains the tables for `Account`, `User`, `Ticket`, `TicketMetadata`, `TicketMessage`, and `Knowledge`. The query returns at least 14 articles covering technical support, billing, accounts, and reservations. Record the run, schema, counts, and example titles. |
| A02 · Architecture and state | Compare the Markdown and Mermaid diagram with the `StateGraph` nodes and edges. Inspect a ticket run for each route. | The observable roles, contracts, routes, state, and messages match the design. At least four specialized agents participate in the expected paths. Record the graph and traces that identify each role. |
| A03 · Sign-in guidance | Chat, normal urgency, `I forgot my password. How can I sign in again?` | The workflow classifies the ticket as account access and routes it to knowledge retrieval and resolution. The response explains the sign-in article's guidance and references its ID. The log shows the category, route, article, and score. |
| A04 · Reservation guidance | Email, normal urgency, `How do I reserve a spot for an event?` | The workflow classifies the ticket as a reservation question and retrieves the corresponding reservation article. The guidance matches the article, and the output includes its reference. Compare the trace with A03 to demonstrate retrieval by topic. |
| A05 · Subscription and account details | In the test database, a verified customer has an active subscription with a quota of seven experiences per month. The general subscription article lists four. The customer asks `What is my subscription status and monthly quota?` In a separate ticket, a verified customer asks `Is my account blocked?` | The account route calls `lookup_subscription` and `lookup_account` in the respective cases. The subscription answer reports the active status and seven experiences per month from the lookup. It uses the relevant article for general guidance and omits the conflicting amount of four from the personalized answer. Verify the account status against SQLite and record the structured results and traces for both cases. |
| A06 · Evidence thresholds and multiple intents | Use a normal-urgency ticket on a topic outside the corpus. In a controlled test, supply candidates scoring 0.59 and 0.60 for the same intent. Test a fabricated reference and an excerpt absent from its article. For a ticket asking about both password reset and event reservations, run once with a relevant article for each intent and once with evidence for only one. | The workflow resolves at 0.60 with valid evidence and resolves the two-intent ticket when both intents independently meet the threshold with valid references. The results show up to three candidates per intent. The workflow escalates with `insufficient_evidence` for an unmatched intent, a score of 0.59, invalid evidence, or a gap in coverage. Record per-intent scores, references, and the escalation reason when applicable. |
| A07 · Metadata and risk | Repeat the A03 message with high urgency. In a separate case, ask the system to issue a refund. | The workflow escalates with a reason that matches the metadata or requested action. The summary states what the customer asked for and which actions were attempted. The trace shows the route for each case. |
| A08 · Validation, failures, and ownership | Select an unknown profile, open a ticket owned by a different synthetic profile, and include a third party's ID in the text of a ticket owned by the active profile. Test a customer without a subscription, then simulate an unavailable CultPass database or model. | The interface rejects an invalid profile and a ticket owned by someone else before accessing history. The ID in the message does not change the identity passed to the tool. A verified customer without a subscription gets `ok` with `has_subscription=false` and can receive guidance grounded in an article. An unavailable database returns `unavailable` and triggers escalation if the lookup is required. A model failure triggers escalation with a template-generated summary. Verify the responses and logs for absence of third-party data. |
| A09 · Session memory and inspection | In the same ticket, ask how to reserve an event, then ask `What should I do next?` Inspect the session checkpoint using `thread_id`. | The second turn recalls the reservation topic and continues with guidance based on the articles. Inspection shows messages, state, and tool results when tools were used. Verify that the route and evidence are recalculated for the turn. |
| A10 · Memory across sessions | Resolve a case in the first ticket and record an explicit request for step-by-step responses. Restart the process and open one new ticket for the same customer and another for a different customer. | The returning customer receives an answer in the requested format with relevant context from the earlier case. The other customer receives their own context. Query the database for the persisted messages, outcome, and preference, then check both responses. |
| A11 · Persisted outcome and retries | Process tickets through resolution and escalation. Resend a completed `turn_id` and simulate a write failure when saving a new turn's outcome. | Both outcomes are stored in SQLite and readable after a restart. A retry returns the saved output without duplicating messages. If the write fails, the interface reports an operational error. Record the queries and failure test results. |
| A12 · Demo and logs | Run A03, A05, and A06 through the documented entry point with the provider configured, using fictional tickets. Search the events by ticket and turn. | The demo includes grounded resolution, tool use, and escalation. The searchable JSON trace shows the classification, route, retrieval, tool use, decision, and outcome where applicable. Record the commands, revision, outputs, and demo limitations. |
| A13 · Self-contained submission | Copy only `solution/` into an isolated directory, install the documented versions, run setup and the test suite, and start the interface. | The package runs with the included inputs and instructions and generates its databases locally. It includes documentation, code, setup notebooks, and tests, and can be evaluated independently of the rest of the repository. Verify the package contents, versions, and command outputs. |

A01 covers data preparation. A02 through A04 cover architecture, routing, and grounded responses. A05 through A08 cover tools, confidence, escalation, and failure handling. A09 through A11 cover state and persistence. A12 and A13 cover the demo, logs, and reproducibility of the submission.
